# A 6502 gem4xe, and what the toolchain will and will not do for it

Status: **prototyped, not started.** This records what was measured, so the
design argument rests on the toolchain's actual behaviour rather than on a
sentence in its manual.

Reproduce everything here with `python3 tools/bsp6502/probe.py`.

## The question

gem4xe needs a 65C816 today. A 6502 build would need banked code, and
Calypsi's 6502 linker has a banking mechanism (`scatter-to`,
`:generate-instances`, a `bankedcode` section) whose documentation says:

> Somewhat simplified, once properly linked, the compiler runtime handles
> the bank system automatically.

Read one way that promises a trampoline on every cross-bank call, which
would make a 6502 port mostly a matter of writing a linker map. Read
another way it promises only that the *relocation arithmetic* is handled.
The difference decides the whole architecture, and no documentation in the
toolchain settles it — there is no worked example of a banked **call**
anywhere in `doc/`, only of banked placement.

So it was asked of the toolchain directly: a resident `main()` in bank
`$00` calling two functions placed in `bankedcode`, linked against a
throwaway Atari map with the PORTB window at `$4000-$7FFF`.

## What came back

**1. A call into banked code is a plain `jsr`.**

```
main:   ...
        jsr  $4260        ; far_a, at its address INSIDE THE SLOT
        jsr  $4000        ; far_b
```

No bank switch, no veneer, no runtime call. The program is responsible for
having the right bank mapped before the `jsr`.

**2. That is not a shortcoming of an unsupported target.** The same two
object files linked against Calypsi's *own* `cx16-banked.scm` — a target it
supports — produce `jsr $A260` / `jsr $A000`: the identical plain call at
the X16's slot address. There is no mechanism being missed. **Banking is
placement, and only placement.**

**3. Two functions in different banks can share one runtime address, and
nothing says so.** With the slot small enough to force several instances,
`far_b` and `t100` both resolve to `$4000`, and `t112` and `t183` both to
`$45E8`. The linker exits 0 and emits no diagnostic; `ln6502` has no
warning, check, or bank-related option at all. In the linked image a
`jsr $4000` is genuinely ambiguous — which function it reaches depends
entirely on what is mapped at the moment it executes.

## What that means for the port

**gem4xe would own the bank register, the way GEOS owns it.** That is a
known-good design, not a blocker. But the third finding is the one to build
around, because it is this project's recurring failure shape: **a wrong
cross-bank call compiles, links silently, and jumps to whatever happens to
be mapped.** It is not a diagnosable error; it is a wrong answer delivered
confidently.

Three consequences follow.

**Everything mutually callable must share a bank, or go through a
resident trampoline.** 16 KB per bank against roughly 216 KB of code (the
current 146 KB of far code times the measured 1.48× the 6502 costs) means
about fourteen banks, so partitioning alone cannot carry it. Cross-bank
calls need a bank-saving trampoline in bank `$00`.

**A post-link gate has to be written, because the toolchain has none.**
The information exists: each bank instance's contents are stored at a
unique address in the scatter destination, so a function's bank is
derivable from the instance layout even though the symbol table does not
record it. A checker can then require that every `jsr`/`jmp` whose target
lies in a different bank from its caller goes through a registered
trampoline. That is a `tools/ccbug/mscan.py`-shaped job, and it is ours to
build — see `make-a-silent-check-fail-first`: it needs a fixture that must
report, or its silence means nothing.

**GEM's 1984 ABI is unusually kind here.** The VDI and AES pass arguments
through fixed global arrays (`contrl`, `intin`, `ptsin`, `intout`,
`ptsout`), and `src/sys/abi.s` already implements the copy-in/copy-out
discipline that goes with them. Put those arrays in resident bank `$00` and
a banked caller and a banked callee never dereference a pointer into
memory that is switched out. The calls that *do* carry pointers —
`objc_draw(tree)`, `rsrc_load`, `form_alert`, `v_gtext`, an MFDB's
`fd_addr` — are exactly the ones the 65C816 build already bounces through a
near buffer for a different reason (`abi-near-of-far-string-bug`), so the
machinery has a precedent in the tree.

## What the machine would be

Encouragingly, not an exotic one:

| | |
|---|---|
| CPU | stock 6502 — **no accelerator** |
| RAM | ≥1 MB PORTB expansion (a 130XE's four banks cannot hold ~216 KB) |
| Video | **no VBXE needed** — the ANTIC driver already ships |
| Storage | SpartaDOS X / APT / CF, all already gated |

The display is genuinely solved rather than promised: `test-m26` boots the
shipped `GEM.COM` on a VBXE machine, on one without, and with
`VIDEO=ANTIC` overriding a working VBXE, with nothing typed in any of the
three. Without a VBXE it runs 320×168 in two colours with Atari's
condensed 6×6 face — **53×28 cells**, which is a usable desktop rather than
a token one.

## The map the BSP would have to define

Bank `$00` today, from `src/gem4xe.scm`, and what a 6502 build does with
each region:

```
$2000-$205A  direct page + registers      91 B   keep
$2100-$373F  LoRAM: zdata/stack/data   5,696 B   keep (95.5% full today)
$3740-$3FFD  Near: resident code       2,238 B   keep (84.9% full today)
$4000-$47F3  zwin (the VBXE window)    2,036 B   freed -- no VBXE
$4800-$7FFF  AppPool                  14,336 B   CONTENDED
$8000-$9B88  far-code staging          6,793 B   freed -- becomes the screen
$A000-$BFFF  unused                    8,192 B   free with BASIC off
```

**`$4000-$7FFF` is the contention and the open design question.** It is the
only switchable window, and gem4xe currently runs a launched application
there. Either the application moves (`$A000-$BFFF` is free with BASIC off,
but that is 8 KB against today's 14 KB), or applications are banked too and
every AES call from one crosses a bank — which the copy-in/copy-out ABI
above makes tractable, and which would incidentally give each application a
whole bank of its own. That second shape is also the one a multitasking AES
would want (`gem4xe-multitasking-request`).

Bank `$00` is already 95.5% and 84.9% full in its two resident memories,
and a banked build needs *more* resident space, not less — for the
trampolines and the bounce buffers. The 2 KB freed by `zwin` and the 8 KB
at `$A000-$BFFF` are where that has to come from.

## Still open

- Which way the `$4000-$7FFF` contention is resolved. Everything else
  follows from it.
- Whether hth313 intends `scatter-to` to be usable this way on a custom
  target, or would rather add a bank-call mechanism. Worth asking with
  these measurements attached — it is a concrete report, not a feature
  request, and it pairs with the 6502 board support already offered on
  Calypsi issue #33.
- `cc6502` accepts `__far` and **silently ignores it** with a warning.
  `src/portab.h` already funnels everything through `FAR`/`NEAR`/`TINY`, so
  the seam exists — but a 6502 build must define them away deliberately and
  compile with unknown-attribute warnings as errors, or every far pointer
  quietly becomes a near one.
